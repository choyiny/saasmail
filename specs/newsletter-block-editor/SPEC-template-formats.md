# Spec: template-formats

> Module `template-formats` of [the newsletter block editor map](./README.md).
> Shared commands, structure, style, testing and boundaries live there.
> Depends on `block-compiler`.

## Objective

Let one `email_templates` row be authored either as raw HTML (today) or as a
block document (new), without any downstream consumer learning that blocks
exist. This is the plumbing module: schema, migration, route changes, and the
compile-on-save wiring.

## Assumptions

1. `bodyHtml` stays `NOT NULL` and stays the rendering source for every path.
2. Existing templates are format `html` and are untouched.
3. Compilation happens **in the worker**, on write — not in the browser — so
   the API is as capable as the UI and the server is authoritative.

## Schema change

```ts
// worker/src/db/email-templates.schema.ts  (additions)
format: text("format", { enum: ["html", "block"] }).notNull().default("html"),
bodyJson: text("body_json", { mode: "json" }).$type<BlockDocument>(),
```

D1 has no JSON column type; drizzle's `mode: "json"` stores text and handles
serialization. `bodyJson` is nullable — it is null for every `html` template.

Generate with `yarn db:generate`. Do not hand-author the SQL. The default on
`format` is what makes this a pure additive migration: every existing row
becomes `html` without a backfill pass.

Keila's equivalent is a column per format plus a `settings.type` enum
(`[:text, :markdown, :block, :mjml, :html]`). We take the discriminator and the
side-by-side storage, but only two of the five formats — see
[the map](./README.md) for why the other three are not worth their weight here.

## Write path

`POST /api/email-templates` and `PUT /api/email-templates/{slug}` gain an
optional `format` and `bodyJson`.

```
format: "html"   → bodyHtml required, bodyJson must be absent      (today's behaviour)
format: "block"  → bodyJson required, bodyHtml must be ABSENT
```

A client-supplied `bodyHtml` on a block template is a `400`, not a silent
overwrite. If both were accepted the two representations would drift, and the
one that actually sends would be whichever the client happened to set.

On a block write the handler:

1. Validates `bodyJson` against `BlockDocumentSchema` (which sanitizes inline
   HTML as part of validation — see `SPEC-block-compiler.md`).
2. Compiles it: `bodyHtml = compile(doc)`.
3. Runs the existing `templateParseError(subject, bodyHtml)` check
   (`email-templates-router.ts:38`) on the _compiled_ output, so a malformed
   `{{#section}}` typed into a block still fails the write with the same
   diagnostic as today.
4. Writes `format`, `bodyJson`, and the compiled `bodyHtml` together.

Step 3 is the reason compilation must precede validation rather than follow it.

## Format conversion

**`block` → `html` is allowed and one-way.** The handler compiles, keeps the
resulting `bodyHtml`, sets `format = 'html'`, and nulls `bodyJson`. The UI must
confirm before sending this, because the block structure is not recoverable.

**`html` → `block` is refused** with `422`. Parsing arbitrary email HTML back
into a block document is a lossy heuristic that would quietly discard layout
the author cannot see is gone. An author who wants blocks starts a new template.

## Read path — the point of the module

Unchanged, everywhere:

| Consumer                                         | Reads          | Change |
| ------------------------------------------------ | -------------- | ------ |
| `snapshotCampaign` (`campaign-sender.ts:92-119`) | `bodyHtml`     | none   |
| `rewriteCampaignLinks`                           | `bodyHtml`     | none   |
| Sequence step sends                              | `bodyHtml`     | none   |
| `POST /api/email-templates/{slug}/send`          | `bodyHtml`     | none   |
| `GET /api/email-templates/{slug}/variables`      | `bodyHtml`     | none   |
| `templateRevision` provenance string             | `id@updatedAt` | none   |

`GET /api/email-templates/{slug}` gains `format` and `bodyJson` in its response
so the editor knows which surface to open. That is the only read-side change.

## Success criteria

- [ ] Migration is generated by `yarn db:generate`, is additive, and applies
      cleanly to a database seeded before the change.
- [ ] Every pre-existing template reads back as `format: "html"` with
      `bodyJson: null` and byte-identical `bodyHtml`.
- [ ] `POST` with `format: "block"` and a valid document persists all three
      columns and returns `201`.
- [ ] `POST` with `format: "block"` and a `bodyHtml` returns `400`.
- [ ] `POST` with `format: "block"` whose compiled output contains an unbalanced
      `{{#section}}` returns `400` with the existing diagnostic naming the tag.
- [ ] A campaign whose template is `format: "block"` snapshots and sends with no
      change to `campaign-sender.ts`. Verified by an existing campaign test
      re-pointed at a block template.
- [ ] `PUT` converting `block` → `html` nulls `bodyJson` and preserves the
      compiled HTML exactly.
- [ ] `PUT` converting `html` → `block` returns `422`.
- [ ] `/doc` reflects the new request/response shapes (`openapi-doc.test.ts`).
- [ ] `yarn test --maxWorkers=4` stays green (94 files / 1096 tests at baseline);
      `npx tsc --noEmit -p tsconfig.app.json` stays at 6 errors.

## Decisions

Resolved 2026-09-04.

1. **No recompile endpoint in v1.** A change to the _default_ theme in code
   leaves existing block templates on their previously compiled HTML until
   someone saves them again. That is consistent with the frozen-content posture
   and avoids an endpoint whose blast radius is every template at once. The save
   path is the recompile.
2. **`docs/templates.md` gains one section, not a new page.** The `{{…}}` rules
   are unchanged; what is new is "which formatting can I put in a block", which
   is the inline-HTML allowlist from `SPEC-block-compiler.md`.
